# Career Kit 产品设计理念

> 项目定位、设计哲学、核心概念

---

## 1. 项目定位

一个 MCP 服务器，把 AI 变成职业规划伙伴。用户告诉 AI 自己的现状和目标，AI 帮忙分析差距、规划路线、拆成阶段任务，执行后持续追踪和调整。

核心链路：**建档 → 差距分析 → 路线图 → 任务 → 打卡 → 调整 → 循环**

核心理念：**顺序归产品，时间归用户。**
- 产品只回答「达成目标需要什么、按什么顺序」，不为任务设定时限
- 每个人的自由时间、学习能力、投入意愿不同，LLM 替用户规划时间是不恰当的
- 用户可能提前完成（有了精力做新规划），也可能滞后——节奏完全由用户自己掌握
- 进度以**阶段**为刻度：每阶段的完成数/总数就是进度条
- 用户想要日程时，LLM 在对话中直接写 markdown/HTML 文档交付，系统不存储日程

---

## 2. 为什么做这个

市面上的职业规划工具要么是一次性的（生成计划就结束），要么只覆盖链路中的某个环节（只做简历、只做岗位搜索、只做面试准备）。没有一个项目把「建档 → 分析 → 规划 → 日程 → 追踪」串成完整闭环，且支持持续更新。

### 核心问题

**求职者从"我想找工作"到"我拿到 offer"之间的路径是模糊的。**

这种模糊导致：
- 不知道差距在哪（技能？经验？简历？）
- 不知道该学什么（优先级、深度、时间分配）
- 不知道市场要什么（JD 写的和实际考核的往往不同）
- 执行过程中无法判断自己是否在正确的轨道上

### 第一性原理推导

**什么是"好的职业规划"**：

不是 LLM 编一段鼓励的话，而是：

```
真实市场数据 × 个人现状 = 可执行的路径
```

三个要素缺一不可：
1. **真实数据** — 市场要什么、别人怎么拿到 offer、面试问什么
2. **个人现状** — 你会什么、缺什么（摸排真实水平，简历有美化成分）
3. **可执行性** — 下一步做什么、怎么验证进度、何时调整

## 3. 技术选型

### 为什么选 MCP Server

| 方案 | 优势 | 劣势 |
|------|------|------|
| Claude Code Skill | 开发简单，零部署 | 锁死在 Claude Code 生态，受众窄 |
| **MCP Server** | **通用协议，Claude/Cursor/Windsurf 都能用，开源受众最广** | 需要懂 MCP 协议 |
| 独立 Agent（Web/CLI） | 最灵活，可以做 UI | 开发重，维护成本高，社区贡献门槛高 |

MCP 是当前 AI 工具开源的通用协议，写一次所有客户端都能调用。先用 MCP 验证核心逻辑，后续如果需要 UI 或主动推送再考虑独立化。

### 技术栈

- Python 3.11+
- FastMCP（MCP Server 框架）
- Pydantic（数据校验）
- 本地 JSON 文件存储（零依赖，隐私友好）

## 4. 数据模型设计哲学

### "骨架固定，血肉自由"

写死的只有 5 个 section：

```json
{
  "who": {},   // 你是谁
  "have": {},  // 你有什么（技能条目建议带 evidence 证据与 confidence 置信度）
  "want": {},  // 你想要什么
  "gap": {},   // 差距是什么
  "plan": {}   // 怎么走
}
```

每个 section 里面放什么，完全由 LLM 根据对话内容自由组织。

### 为什么这样设计

- **写死字段**：能精确计算，但覆盖不了千差万别的用户情况（应届生、转行者、自由职业者需要完全不同的字段）
- **全开放**：灵活，但没法做自动化分析和规划
- **骨架固定 + 血肉自由**：tool 认识 5 个 section 的语义（知道 `have` 是现状、`want` 是目标），但不解析具体内容。LLM 负责理解和组织每个 section 的内容

### 跨会话一致性

靠 `summary` 字段而不是 schema 约束。每次更新后 LLM 生成一段摘要，下次对话先读摘要理解上下文。摘要是 LLM 之间的"交接文档"。

### 能力证据沉淀

简历有美化成分，简单简历不能反映用户真实水平：
- **建档时**：对关键技能追问证据（做过什么项目、讲一个难点），have 条目带 evidence/confidence
- **执行中**：任务完成打卡时自动把「任务名+备注+时间」沉淀进 have.capability_evidence
- **目标变更时**：已完成进度直接作为能力补充参与重新分析——努力不白费

### 知识光谱与 jd 三件套（数据真实性纪律贯通到路线图）

数据真实性不是二值（真实/编造），而是**知识置信度光谱**：
- **稳定常识**（公司名、选人特点如「某司卡学历/欢迎双非」、行业形态）→ LLM 知识可靠，自由写
- **时效事实**（具体 JD 细节：岗位职责、技能要求、薪资、在招状态）→ 必须有真实数据支撑

路线图阶段以 **jd 三件套** 承载这条纪律：
- `company` + `rationale`：常识，自由写（含选人特点判断）
- `jd`：时效事实，有真实数据（抓取/导入）才填，否则保持空
- `jd_status`：has_jd / pending_user_import / not_required；`confirmed` 记录用户是否已确认「先占位后补JD」

### 起点层级（gap.start_level）

差距分析产出 `gap.start_level`（当前可进入的企业层级：大厂/中厂/小厂），
路线图设计消费它对齐起点——目标层级超起点时插入过渡阶段（公司名可写、JD 细节占位），
用户导入真实 JD 后由目标变更检测自动触发细化闭环。这是「计划→执行→新数据→修订」
螺旋的一环，与能力证据沉淀同构。

## 5. 建档流程设计

### 状态机引导，而非一次性提取

不是让用户一次说完所有信息，而是用状态机逐步引导：

```
start_session → "你现在是什么状态？"
    ↓
intake(who) → "你目标是什么方向？"
    ↓
intake(want) → "你现在会什么？（关键技能追问证据）"
    ↓
finalize_profile → 生成摘要，进入分析
```

每一步 LLM 可以追问、确认、纠偏。比"请告诉我你的情况"好得多。

### 为什么不用一次性 create_profile

- 用户不知道该提供什么信息
- 一次说完容易遗漏关键信息
- LLM 可以根据前一步的回答动态调整下一个问题

## 6. MCP Tools 设计

按工作流阶段分组（当前 24 个）：

### 建档阶段（状态机）

| Tool | 输入 | 输出 | 说明 |
|------|------|------|------|
| `start_session` | 无 | 欢迎信息 | 初始化新档案 |
| `parse_resume` / `import_jd(_file)` | 文件/文本 | 解析结果 | 简历与 JD 导入 |
| `intake` | section + data | 确认信息 | 逐步填充 who/have/want（技能带证据） |
| `finalize_profile` | 无 | 摘要 | 确认档案完整，解锁分析工具 |

### 数据获取阶段

| Tool | 输入 | 输出 | 说明 |
|------|------|------|------|
| `list_data_sources` | 无 | 企业源清单 | 查看可用 scraper 和参数 |
| `get_scraper_guide` | company | 使用教程 | 首次使用某数据源前读取 |
| `fetch_company_jobs` | company + params | 岗位列表（含薪资） | 实时抓取，自动写入知识库 |
| `fetch_jd_detail` | url | JD 全文 | 获取岗位详情 |
| `search_knowledge` | query | 本地资料 | 只查知识库，不联网 |

### 分析规划阶段

| Tool | 输入 | 输出 | 说明 |
|------|------|------|------|
| `analyze_gaps` / `save_gap_analysis` | gap_json | 差距分析 | 对比 have/want 与真实 JD |
| `generate_roadmap` / `save_roadmap` | roadmap_json | 路线图 | 分阶段计划，无时长字段 |

### 任务执行与洞察阶段

| Tool | 输入 | 输出 | 说明 |
|------|------|------|------|
| `generate_tasks` | 无 | 任务列表 | 从路线图生成任务；重建时历史进度沉淀为能力证据 |
| `get_next_tasks` | 无 | 当前阶段下一步 | 关卡式：顺序即答案 |
| `checkin_task` | task_id | 打卡结果 | 完成自动沉淀能力证据 |
| `trigger_insight` / `apply_insight` | trigger_type | 调整记录 | 仅 stage_audit / event 两种触发 |
| `get_progress` / `get_workflow_status` | 无 | 进度/状态 | 含目标变更检测 |
| `export_dashboard` | 无 | 自包含 HTML | 阶段驱动仪表盘快照 |
| `import_plan` | file_path | 解析结果 | 导入既有规划文档，对比取舍在对话中完成 |

### 核心循环

```
用户目标 → fetch_company_jobs（真实数据）
    → analyze_gaps → save_gap_analysis
    → generate_roadmap → save_roadmap
    → generate_tasks → get_next_tasks
    → 用户打卡 checkin_task（能力证据自动沉淀）
    → trigger_insight(stage_audit/event) → apply_insight（调整）
    → 回到任务执行
```

每一轮循环都让规划更精确。

### 工具面设计四原则

1. **一个用户意图 ↔ 唯一工具入口**——双入口会让 LLM 混乱
2. **返回值即指引**——下一步做什么写进返回值
3. **诚实的能力边界**——无数据就明说并给替代路径，绝不引导编造
4. **单一指导源**——工作流知识只在 session.py 维护

## 7. 数据从哪来

| 数据类型 | 来源 | 可信度 |
|----------|------|--------|
| 岗位要求（JD） | 企业 scraper 实时抓取 | ⭐⭐⭐⭐⭐ 真实 |
| 薪资数据 | JD 中的薪资范围（fetch_company_jobs 汇总） | ⭐⭐⭐⭐⭐ 真实 |
| 面试经验 | 牛客 scraper 抓取 | ⭐⭐⭐⭐ 真实但主观 |
| 成功案例 | 知识库积累（简历/面经） | ⭐⭐⭐⭐ 可对标 |

**核心判断**：
- 分析必须基于真实抓取的数据，LLM 知识不作为分析依据
- 无数据时诚实告知并引导用户走抓取链路，绝不静默降级到 LLM 编造
- 不预置知识库内容，只提供填充途径
- 数据获取通过企业爬虫，不依赖外部搜索 API

## 8. 设计原则

### 8.1 开源项目原则

1. **不预置知识库内容**：开源项目只提供填充途径，不提供数据
2. **数据获取通过爬虫**：企业 Scraper 是主要数据源，不依赖外部搜索 API
3. **LLM 自身有搜索能力**：无需额外接入 Web Search API

### 8.2 爬虫框架原则

1. **只定义接口，不提供通用模板**：每个网站独立实现，千人千面
2. **接口规范清晰，实现自由度高**：降低社区贡献门槛
3. **数据自动积累**：爬虫抓取的数据自动写入知识库

### 8.3 分析流程原则

1. **SOP 驱动**：分析流程由 YAML 配置定义，可版本控制
2. **数据优先**：真实数据 > LLM 知识，本地数据 > 实时抓取
3. **反馈闭环**：用户反馈影响下次分析，形成迭代改进
